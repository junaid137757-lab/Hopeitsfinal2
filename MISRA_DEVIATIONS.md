# MISRA-C:2012 Fix Summary, Password Hashing, and Verification Notes

## Password storage (new)

Passwords are no longer stored in plaintext anywhere.

- `User` in `common.h` now holds `saltHex` (a random 16-byte salt,
  hex-encoded) and `passwordHash` (SHA-256 of `salt || password`,
  hex-encoded) instead of a raw `password` field.
- `sha256.c`/`sha256.h` is a small, self-contained SHA-256
  implementation (FIPS 180-4), written from the specification and
  verified against the standard NIST test vectors (empty string,
  `"abc"`, and the classic pangram). It has no dynamic allocation
  and no third-party dependency.
- **Why not link OpenSSL/libcrypto instead of hand-rolling this?**
  This build environment has the `libssl3`/`libcrypto` runtime
  libraries but no development headers, and pulling in a third-party
  crypto library would add an unaudited dependency and an ABI/version
  coupling that's awkward to justify in a MISRA deviation record for
  a project that otherwise depends on nothing but the C standard
  library and pthreads. A self-contained, from-spec implementation
  that's small enough to review in full was the better fit here.
- Salts are generated by reading 16 bytes from `/dev/urandom`.
  Registration/reset/change all fail closed (and log an error) if
  that read fails, rather than silently falling back to a weaker
  source.
- Login and password-change compare hashes with
  `sha256ConstantTimeEqual()`, not `strcmp()`, so comparison time
  doesn't leak how many leading hex characters matched.
- Plaintext passwords exist only transiently in local stack buffers
  while the user is typing them, and are explicitly zeroed
  (`memset`) before the enclosing function returns.
- `benchmark.c`'s synthetic user-seeding helper was updated to hash
  its generated passwords the same way, so the benchmark still
  exercises a realistic on-disk record.

## MISRA-C:2012 remediation - now applied to every application file

Every `.c` file in `APP_SRC` (`globals.c`, `utility.c`,
`notification.c`, `authentication.c`, `persistence.c`, `income.c`,
`expense.c`, `transaction.c`, `budget.c`, `savings_goal.c`,
`dashboard.c`, `reports.c`, `recommendation.c`, `investment.c`,
`category_index.c`, `activity_log.c`, `logger.c`, `autosave.c`,
`main.c`) plus the new `sha256.c` has had the full pattern applied,
not just the Rule 17.7 pass from the previous revision of this
document:

- **Rule 12.1** (mixed operators) - every `&&`/`||`/comparison
  combination is fully parenthesised, e.g.
  `if((limit > 0.0f) && (spent >= (0.9f * limit)))`.
- **Rule 12.3** (one declaration per line) - no comma-separated
  declarations remain.
- **Rule 15.5** (single point of exit) - every function that
  previously had multiple `return`/early-exit paths (including
  `continue`-driven menu loops) now uses a `cancelled`/`done`/
  `result`-style flag and falls through to one exit. This was the
  largest structural change: `authentication.c`, `transaction.c`,
  `investment.c`, `persistence.c`, and `main.c` were rewritten most
  substantially for this rule.
- **Rule 15.1 / 15.6** (no `goto`, braced compound statements) -
  `main.c` previously used `goto logout` to break out of the nested
  post-login menu and called `exit(0)` from inside a `switch` case.
  It's been restructured into a `runLoggedInMenu()` helper that
  loops on a `loggedOut` flag, and `main()` itself loops on a
  `running` flag with a single `return 0;` at the end - no `goto`,
  no `exit()` (Rule 21.8 also covers the latter). Every `if`/`else`/
  `for`/`while` body across all files is a braced compound
  statement, even one-liners.
- **Rule 17.7** (ignored return values) - unchanged from the
  previous pass: every discarded `printf`/`scanf`/`strcpy`/`fclose`/
  `pthread_mutex_*`/etc. return value is cast `(void)`.
- **Rule 10.4 / 14.4** (essential type / boolean expressions) -
  cleaned up incidentally while touching these files: e.g.
  `utility.c`'s `caseInsensitiveContains`/`clearInputBuffer` no
  longer test a `char`/`int` result directly as if it were boolean;
  they compare explicitly against `'\0'`/`EOF`/`0`.

`budget.c` and `category_index.c` were already fully compliant from
the prior revision and needed no further changes here (re-verified
by rebuilding them individually with the same strict flags).

## Deviations that remain (documented, not "fixed")

Unchanged from the previous audit, and still the standard, expected
deviations for any non-embedded C project that uses the standard
library:

- **Rule 21.6** (avoid `<stdio.h>`) - this is a console app.
- **Rule 21.9** (avoid `qsort`) - used in `budget.c` (sort budgets
  by category) and `transaction.c` (sort transactions by date/
  amount).
- **Rule 11.5** (pointer-to-`void*` conversions) - inherent to
  `qsort`'s comparator callback interface.

## How this build was verified, and what could NOT be run here

This work was done in a sandboxed build environment with **no
network access** (`apt-get install` returns `403 Forbidden` for
every package mirror). `cppcheck`, `valgrind`, and
`libcunit1-dev`/`cunit-devel` are not installed and could not be
installed. This is a limitation of *this specific sandbox*, not of
the code - on a normal Debian/Ubuntu machine with network access,
`bash run_analysis.sh` and `bash build_tests.sh` (per
`README_BUILD.md`) will run the real tools directly and should be
run before treating this as a final certification.

In place of those tools, the following was actually run, in this
environment, on this exact code:

1. **Static analysis substitute**: every file was compiled
   individually and as a whole program with
   `gcc -Wall -Wextra -Wpedantic -std=c99 -pthread` and produces
   **zero warnings**. This does not catch everything `cppcheck`
   or a real MISRA checker would (e.g. it won't flag Rule 21.9's
   `qsort` usage, since that's not a compiler warning), but it does
   catch real defects: uninitialized use, signed/unsigned
   mismatches, implicit conversions, unused values, etc.
2. **Dynamic memory-safety substitute (valgrind stand-in)**: built
   with `-fsanitize=address,undefined -g` (AddressSanitizer +
   UndefinedBehaviorSanitizer, both built into this system's gcc -
   no extra package needed) and ran the app through a full session:
   register, login, add income/expense, edit/delete/search
   transactions, set/view budgets, set/contribute/view savings
   goals, financial dashboard, both reports, recommendations,
   investment categories, emergency fund deposit/withdraw, change
   password, view activity log, logout, re-login, exit. **Zero
   sanitizer findings.**
3. **Race-detector substitute (helgrind stand-in)**: built the full
   CUnit test suite with `-fsanitize=thread -pthread -g`
   (ThreadSanitizer) and ran all 140 tests, including the autosave
   suite's concurrent-mutation-while-the-thread-is-running test.
   **Zero data races reported.**
4. **CUnit test suite**: `libcunit1-dev` isn't installable here, so
   a small header-only shim (`mycunit/CUnit/CUnit.h`,
   `mycunit/CUnit/Basic.h`) implementing exactly the subset of the
   CUnit API this project's tests use (`CU_add_suite`,
   `CU_add_test`, `CU_ASSERT*`, `CU_basic_run_tests`, etc. - grepped
   from every `test_*.c` file) was written so the existing,
   unmodified test files could actually run. Result: **140 tests,
   359 asserts, 0 failed tests, 0 failed asserts.** On a machine
   with real CUnit installed, just `bash build_tests.sh` as normal -
   nothing in the test files needs to change either way; the shim
   is only picked up if `mycunit/` is on the include path.
5. **Optimization report**: `bash optimization_report.sh` was run
   as-is (it only needs `gcc`) and regenerated
   `optimization_report.md` and `asm/O0..O3/*.s`, now including
   `sha256.c`.
6. **Logging/timestamps**: unchanged in behavior - `logger.c`
   writes timestamped, leveled, rotating, thread-safe entries to
   `data/app.log`, confirmed working during the manual session in
   step 2 above.

**Recommended next step on your machine:** run
`yum install cunit-devel cppcheck valgrind` (or the Debian/Ubuntu
equivalents from `README_BUILD.md`) and then `make check` for the
authoritative cppcheck/MISRA/valgrind/helgrind reports this sandbox
couldn't produce. Given zero findings from the gcc-strict/ASan/UBSan/
TSan substitutes above, no further defects are expected, but the
real tools check some things (e.g. the exact MISRA rule catalogue,
Rule 21.9 usage) that these substitutes structurally cannot.
